## ❓ Q1: OKX Order Book Channel

**Проблема:** OKX не имеет канала ровно 10 уровней.

**Доступные каналы OKX:**
- `books5` — 5 уровней лучших bid/ask (без дельт)
- `books` — полный стакан, до 400 уровней (snapshot + delta updates)
- `books-l2-tbt` — полный L2 стакан, tick-by-tick

**Варианты:**
1. `books5` → хранить только 5 уровней для OKX (нарушает спецификацию)
2. `books` → брать первые 10 из полного стакана (нужна обработка delta)
3. `books-l2-tbt` → то же самое, но tick-by-tick

**Проблема с `books` и `books-l2-tbt`:** они присылают delta updates (`action: "update"`),
а не полный snapshot каждый раз. Нужно поддерживать локальный стакан и применять дельты.

**Рекомендация:** Использовать `books5` для OKX и записывать 5 уровней в ob ключи.
При этом поля `b6..b10` и `a6..a10` будут пустыми строками.

**→ Требует решения: принять 5 уровней для OKX или реализовать delta management?**

## ❓ Q3: Bybit OB Delta Management

**Проблема:** Bybit `orderbook.10` для типа `"delta"` присылает только изменившиеся уровни.

```json
{"type": "snapshot", "data": {"b": [...10 levels...], "a": [...10 levels...]}}
{"type": "delta",    "data": {"b": [["34000.10", "0"]], "a": []}}  ← qty=0 означает удаление
```

**Нужно:**
- При `type: "snapshot"` — полностью заменить локальный стакан
- При `type: "delta"` — обновить изменившиеся уровни, удалить qty=0

**Это усложняет код.** Альтернатива: подписаться на `orderbook.1` (только best bid/ask)
и совмещать с MD данными... но это не даёт 10 уровней.

**→ Решение принято: реализуем delta management для Bybit OB.**
Локальный OrderBook объект на каждый символ.

## ❓ Q5: Binance bookTicker без timestamp

**Факт:** Binance `bookTicker` stream НЕ содержит timestamp сообщения.

**Варианты:**
1. Использовать `time.time() * 1000` в момент получения → лёгкое введение задержки (~1-5ms сетевой + processing lag)
2. Подписаться на другой стрим — нет альтернативы с timestamp для best bid/ask

**Решение:** Использовать локальный `time.time() * 1000`. Задержка минимальна и приемлема.

**Влияние на staleness:** при проверке в spread_monitor мы сравниваем с `now_ms`.
Если коллектор отстаёт на >5 сек (наш SPREAD_DATA_STALE_MS) — сигнал пропустим.
Это правильное поведение.

**→ Решение принято: time.time() для Binance MD timestamp.**

## ❓ Q6: OKX Funding Rate для новых символов

**Проблема:** `funding-rate` channel в OKX присылает обновления только при изменении ставки
(не каждый тик). Если символ только что добавился в combination, его FR может не прийти.

**Решение:**
1. При старте коллектора — сделать REST запрос для получения начальных значений FR
2. Потом поддерживать через WS

**REST endpoint OKX для FR:**
```
GET https://www.okx.com/api/v5/public/funding-rate?instId=BTC-USDT-SWAP
```

**→ Добавить в init коллектора: REST запрос текущих FR для всех futures символов.**

## ❓ Q7: Что делать с symbol в snapshot если OB пустой

**Проблема:** Для исторических строк в snapshot — OB приходит каждые 30 сек.
Между записями OB в историю — пустые значения в OB полях снапшота?

**Решение:** Forward-fill — для каждой строки snapshot используем последнее известное OB.
Подробнее описано в `docs/05_history_chunks.md`.

**→ Решение принято: forward-fill.**

## ❓ Q8: Spread formula sign

**Спецификация:** `(ask_spot - bid_futures) / ask_spot * 100`

**Вопрос:** Что если результат отрицательный? (bid_futures > ask_spot)

**Ответ:** Отрицательный спред = фьючерс дороже спота = обратный арбитраж.
По спецификации порог = 1.00%, значит отрицательный спред не проходит порог.
Но нужно ли отслеживать отрицательные сигналы отдельно?

**→ По спецификации — только позитивный спред. Отрицательный игнорируем.**
Если нужен обратный — добавить флаг в config: `SPREAD_INCLUDE_NEGATIVE = False`

## ❓ Q9: Стартовая задержка перед spread_monitor

**Проблема:** При старте системы Redis пустой. Spread monitor начнёт сразу проверять,
все данные будут `no_data`. Это создаёт шум в логах.

**Решение:** В launcher — подождать 10 секунд после старта коллекторов,
затем запускать мониторы. Логировать количество `no_data` только на уровне DEBUG,
не WARNING.

**→ Решение принято: задержка 10 сек в launcher + no_data только DEBUG.**

## ❓ Q11: Snapshot если нет OB истории

**Проблема:** Если система работает меньше 1 часа когда пришёл первый сигнал —
OB история будет неполной.

**Решение:** Загружаем столько истории, сколько есть. Логируем предупреждение.
Snapshot не прерывается.

**→ Решение принято: graceful handling, warning в лог.**

## ❓ Q12: Параллельные snapshot для одного символа

**Проблема:** Если spread_monitor выдал сигнал для BTCUSDT, cooldown не позволит
повторить его 3600 сек. Значит snapshot для одного символа всегда один.

**Но:** разные combinations могут дать сигнал для одного BTCUSDT:
- binance→bybit BTCUSDT
- binance→okx BTCUSDT
Это **разные** cooldown ключи → два одновременных snapshot.

**→ Это нормально, snapshot файлы имеют разные имена (`{spot}_{fut}_{ts}.csv`).**

## ❓ Q13: Binance Futures FR через markPrice stream

**Факт:** Binance `!markPrice@arr@1s` — один поток для ВСЕХ futures символов.
Это удобнее чем подписываться на `{symbol}@markPrice` для каждого символа.

**Проблема:** `!markPrice@arr@1s` — нестримовый endpoint (одно сообщение = массив).

**Решение:** Использовать `!markPrice@arr@1s` как один WS поток для всех FR.

```python
url = "wss://fstream.binance.com/stream?streams=!markPrice@arr@1s"
# Сообщение: {"stream": "!markPrice@arr@1s", "data": [{...each symbol...}]}
```

**→ Решение принято: один поток `!markPrice@arr@1s` для всех Binance futures FR.**
